# ADR-0003 — Шифрование содержимого сейфа и выдача текстового блока

Статус: **принято владельцем (решения 1–4 ниже, комментарий в PR #188); независимое криптографическое ревью остаётся обязательным до реальных данных** (#152). До этого — только синтетические данные. Опирается на решения D7 (границы доверия) и D8 (recovery-код владельца) в `docs/mvp-contract.md`; новых продуктовых обещаний не вводит.

## Что защищаем и от кого
- **Защищаем**: текст блока и ключи расшифрования от сервера в покое (БД, бэкапы, логи, письма, администратор БД).
- **Не защищаем** (честно, D7): от оператора, который управляет сервером и доставляемым клиентским кодом (может подменить JS или выдать раньше срока). От потери ключей — только по пути из D8.

## Примитивы (только стандартный WebCrypto, без собственных алгоритмов)
| Назначение | Примитив |
|---|---|
| Шифрование блока | AES-256-GCM, случайный 96-бит IV на каждое шифрование, ключ блока DEK (256 бит, случайный) |
| Ключ сейфа MK | 256 бит, случайный; оборачивает DEK блоков (AES-256-GCM) |
| Ключ получателя | пара RSA-OAEP 3072, SHA-256; открытая часть — SPKI (base64), закрытая не покидает браузер получателя |
| Упаковка DEK под получателя | RSA-OAEP, label = контекст блока |
| Recovery-код владельца | 256 бит случайных, показывается один раз; KEK = HKDF-SHA256(код, соль = id сейфа, info = `afterlight/mk-wrap/v1`) оборачивает MK |
| Резервная копия ключа получателя | файл у получателя: PBKDF2-SHA256 (600 000 итераций) + AES-256-GCM; на сервер не отправляется |
| Отпечаток ключа | SHA-256 (hex) строки открытого ключа без внешних пробелов (тот же, что считает сервер, #167) |

RSA-OAEP выбран за простоту и однозначность в WebCrypto (прямая упаковка DEK без собственной KDF-схемы). Переход на ECDH возможен только отдельным решением с новой версией формата.

## Форматы (версионированы)
- **Конверт шифротекста v1** — строка `v1.<iv>.<ct>` (base64url, `ct` включает тег GCM). Неизвестная версия отклоняется.
- **AAD (контекст)** — `afterlight/v1/<вид>/<id сейфа>/<id блока>`: шифротекст нельзя перенести в другой блок или сейф; подмена контекста даёт ошибку расшифрования. Для упаковки под получателя тот же контекст идёт в label RSA-OAEP.
- Упакованный DEK — base64 (RSA-OAEP), упакованный MK и DEK у владельца — конверт v1.

## Потоки
1. **Создание сейфа (браузер владельца)**: генерируется MK и recovery-код; на сервер уходит только `mkWrapped` = конверт MK под KEK из кода. Код показывается один раз; владелец сохраняет его сам.
2. **Блок**: клиент сам выбирает UUID блока (он входит в AAD, сервер подставить свой уже не может); DEK → шифротекст блока (AAD с id сейфа и блока) и `dekWrapped` = конверт DEK под MK. Сервер хранит шифротекст как непрозрачный текст и проверяет только формат и размер.
3. **Новое устройство владельца**: вводит recovery-код → MK → читает/редактирует блоки. Сброс пароля к MK доступа не даёт (D8).
4. **Получатель** (заранее): входит с подтверждённым адресом, генерирует пару, заявляет открытый ключ (`PUT /recipients/me/key`), **обязательно** сохраняет резервный файл ключа; закрытый ключ остаётся в браузере. Отпечаток сообщается владельцу вне сервера, владелец подтверждает его (#167).
5. **Назначение (владелец, онлайн, заранее)**: DEK оборачивается под подтверждённый ключ получателя; сервер принимает упаковку только под подтверждённый отпечаток. После события владельцу ничего делать не нужно.
6. **Выдача**: после `Finalized` назначенный получатель запрашивает шифротекст и свою упаковку DEK. Сервер заново проверяет право по единым операциям #150 (событие финализировано, не отменено, сейф `Released`, получатель назначен, упаковка действительна для его подтверждённого ключа) и отдаёт **только этот блок и эту упаковку**; не отдаёт ничего верификаторам, по публичным ссылкам и до `Finalized`. Расшифрование — в браузере получателя.

## Ограничения и остаточные риски (явно)
- Потеря **recovery-кода и устройств владельца** = потеря возможности читать и менять своё содержимое; уже назначенный получатель по-прежнему расшифрует (D8).
- Потеря **ключа получателя без резервного файла** = его блок не расшифровать; новая упаковка потребует владельца онлайн (нарушает «владелец офлайн»), поэтому резервный файл обязателен при активации.
- Сервер в момент выдачи видит только шифротекст и упакованные ключи; **когда** выдавать — решает сервер (D7), криптографической защиты от преждевременной выдачи нет.
- Метаданные (размер, время, число получателей, адрес получателя) серверу известны.
- Хранение первой итерации: шифротекст в PostgreSQL (`block.ciphertext`), объектное хранилище S3 в РФ — второй срез (#172); это явное упрощение.
- Файлы и публичные ссылки выключены (#167, #171).

## Решения владельца (принято 2026-10-01)
1. **RSA-OAEP 3072** для упаковки DEK под получателя (не ECDH P-256 + HKDF).
2. **Резервный файл ключа получателя обязателен** при активации: без него получатель не завершает настройку ключа.
3. **Шифротекст первого среза хранится в PostgreSQL** (`block.ciphertext`); объектное хранилище S3 в РФ — второй срез (#172).
4. **Серверной копии закрытого ключа получателя нет** (даже зашифрованной парольной фразой): это дало бы офлайн-подбор слабой фразы.

Это решения по схеме, а не заключение криптографа: независимое ревью до реальных данных по-прежнему требуется.

Хранение ✅ (реализовано): `block.ciphertext`, проверка формата на сервере (`apps/api/src/common/envelope.ts`: упакованный ключ — ровно `v1.<16>.<64>`, шифротекст — `v1.<16>.<≥22>` до 60 000 символов, упаковка под получателя — ровно 384 байта), создание и чтение блока владельцем, ключ сейфа задаётся браузером один раз (`PUT /vaults/:id/key`), серверная генерация `mkWrapped` убрана.
